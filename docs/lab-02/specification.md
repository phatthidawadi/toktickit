# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a responsive, production-quality Requester-facing IT Support Ticketing MVP for TokTickIT. By the end of Sprint 2, Requesters can select a Development Requester identity, create IT tickets with permitted file attachments, receive a unique Ticket Number, search/filter/sort/page through their own tickets, view ticket details in read-only mode, and manage attachments (including soft removal with reason tracking), all adhering to Spec-Driven Development, the Zen Green Theme, and full test coverage.

---

## 2. Stakeholder Request Interpretation
The IT department needs a professional, web-based support ticketing experience for end users (Requesters). The system must allow users to describe problems, pick relevant categories and systems, assign priority, attach supporting evidence, and track ticket status. Submission generates a unique official Ticket Number. To support testing prior to full authentication in Lab 3, a simulated Development Requester Selection mechanism is required to switch testing contexts while maintaining strict data ownership isolation between Requesters.

---

## 3. Scope

### Included
- **Development Requester Selector**: Simulated login context switcher for testing.
- **Create Ticket**: Form capturing Summary, Description, Category, Related System, Priority, and permitted File Attachments.
- **Ticket Number Generation**: Backend generation of unique official Ticket Numbers (`TKT-YYYY-XXXXXX`).
- **My Tickets**: Requester-owned ticket list with search, filter (Category, Priority, Status), sort, pagination, and empty/loading states.
- **Ticket Detail**: Read-only view of ticket details and metadata for the ticket owner.
- **Attachment Lifecycle**: Upload (max 5MB, max 5 files, JPG/PNG/WEBP/PDF), download, metadata display, and soft removal with mandatory reason input.
- **Zen Green UI Theme**: Reusable design system across desktop, tablet, and mobile viewports.

### Excluded
- Real authentication, passwords, sessions, tokens, or role-based authorization (deferred to Lab 3).
- IT Staff workflow, dashboard, ticket assignment, IT Priority modification, or Actions Taken.
- Public comments, internal notes, or ticket status lifecycle changes beyond initial `NEW` status.
- Admin management functions.

## 4. Functional Requirements

- **FR-01**: The system shall provide a Development Requester Selector screen allowing testers to choose an active Requester context before accessing ticketing screens.
- **FR-02**: The system shall display the currently selected Requester in the application shell header with a clear action to change the selection.
- **FR-03**: The system shall allow Requesters to submit a new ticket with Category, Related System, Requested Priority, Summary, Description, and optional attachments.
- **FR-04**: The backend shall automatically generate a unique, official Ticket Number upon successful ticket creation.
- **FR-05**: Every newly created ticket shall automatically begin with status `NEW`.
- **FR-06**: The system shall display a paginated list of tickets owned exclusively by the currently selected Requester under "My Tickets".
- **FR-07**: The My Tickets view shall support keyword search (matching Ticket Number, Summary, Description) and filtering by Category, Requested Priority, and Status.
- **FR-08**: The My Tickets view shall support sorting by Ticket Date, Priority, or Status.
- **FR-09**: The system shall allow ticket owners to view full details of their ticket in a read-only Ticket Detail screen.
- **FR-10**: The backend shall enforce strict ownership checks; requests for tickets or attachments belonging to a different Requester shall be rejected with HTTP 403 Forbidden.
- **FR-11**: The system shall support uploading permitted attachments (JPG, JPEG, PNG, WEBP, PDF; ≤ 5 MB per file; max 5 active attachments per ticket).
- **FR-12**: The system shall allow ticket owners to download active attachments and perform soft removal by providing a mandatory removal reason. Soft-removed attachments shall remain visible as metadata but download/preview access shall be disabled.

## 5. Business Rules

- **BR-01**: **Ticket Number Format**: The official Ticket Number is system-generated by the backend in the format `TKT-YYYY-XXXXXX` (where `YYYY` is the 4-digit current year and `XXXXXX` is a 6-digit zero-padded sequential number, e.g. `TKT-2026-000001`) and cannot be modified by the user.
- **BR-02**: **Initial Ticket Status**: All new tickets start in status `NEW`.
- **BR-03**: **Development Requester Selector**: The selector is for testing purposes only and does not constitute secure authentication.
- **BR-04**: **Active Requester Restriction**: Only active Development Requesters can be selected or create tickets. Inactive Requesters must be excluded from the selector.
- **BR-05**: **Ownership Isolation**: A Requester can only view, search, or manage attachments for tickets where `requesterId` matches their currently selected context.
- **BR-06**: **Field Validation**:
  - **Summary**: Required, trimmed length between 5 and 100 characters.
  - **Description**: Required, trimmed length between 10 and 1000 characters.
  - **Category**: Required, must be a valid active Category ID.
  - **Related System**: Required, must be a valid active Related System ID.
  - **Requested Priority**: Required, must be one of `LOW`, `MEDIUM`, `HIGH`, `URGENT`.
- **BR-07**: **Attachment Rules**:
  - **Allowed MIME types**: `image/jpeg`, `image/png`, `image/webp`, `application/pdf`.
  - **Max File Size**: 5 MB (5,242,880 bytes).
  - **Max Active Attachments**: 5 attachments per ticket.
- **BR-08**: **Soft Removal**: Attachment removal must be a soft delete (`isRemoved = true`). The removal reason is required (min 5 chars).
- **BR-09**: **Removed File Access**: Files marked as soft-removed cannot be downloaded or previewed, but metadata (filename, size, removal reason, removed timestamp) remains readable.
- **BR-10**: **Search & Filter Rules**: Searching is case-insensitive. Default page size is 10 items. Default sorting is Ticket Date descending.
- **BR-11**: **Duplicate-Submission Prevention**: To prevent duplicate ticket creation from multiple rapid clicks or slow networks, the form submission button enters a disabled busy state immediately upon submission until the API response resolves.
- **BR-12**: **Failure Behavior & Form State Preservation**: If ticket submission fails due to network disconnection or backend API error (e.g. HTTP 500/503), all user-entered form values (Category, Related System, Priority, Summary, Description, and selected attachments) must remain strictly preserved in local component state. A top-level error alert is shown, allowing the user to correct or retry without re-entering data.
- **BR-13**: **Attachment Transaction & Compensation Strategy**: Ticket creation and file attachment uploads operate in a two-stage process. If ticket creation succeeds but an attachment upload fails (e.g. upload stream interrupt or storage full), the Ticket is retained in status `NEW` with its official Ticket Number, and the system notifies the user with a warning alert containing an option to retry uploading attachments directly from the Ticket Detail view.

## 7. Data Changes (Prisma Schema)

### Models
- **`RequesterUser`**: `id`, `name`, `email` (unique), `department`, `isActive`, `createdAt`, `updatedAt`.
- **`Category`**: `id`, `name` (unique), `description`, `isActive`, `createdAt`.
- **`RelatedSystem`**: `id`, `name`, `description`, `categoryId`, `isActive`, `createdAt`. Unique constraint on `[name, categoryId]`.
- **`Ticket`**: `id`, `ticketNumber` (unique), `summary`, `description`, `requestedPriority`, `currentStatus`, `requesterId`, `categoryId`, `relatedSystemId`, `createdAt`, `updatedAt`.
- **`Attachment`**: `id`, `ticketId`, `filename`, `originalName`, `mimeType`, `size`, `filePath`, `isRemoved`, `removedReason`, `removedAt`, `createdAt`.

### Database Indexes & Optimization Decisions
- `Ticket`: `@@index([requesterId])` for foreign key lookups.
- `Ticket`: `@@index([requesterId, createdAt])` composite index to optimize paginated ticket list queries filtered by Requester ID and sorted by creation date descending.
- `Ticket`: `@@index([categoryId])`, `@@index([requestedPriority])`, `@@index([currentStatus])` for frequent list filtering.
- `Attachment`: `@@index([ticketId])` for ticket attachment joins.

## 8. API Contract Summary

- `GET /api/requesters`: Retrieve list of active Development Requesters.
- `GET /api/categories`: Retrieve active Ticket Categories.
- `GET /api/related-systems`: Retrieve active Related Systems.
- `POST /api/tickets`: Create a new ticket (Headers: `x-requester-id`).
- `GET /api/tickets`: Query requester-owned tickets (Params: `search`, `categoryId`, `priority`, `status`, `sort`, `page`, `limit`).
- `GET /api/tickets/:id`: Retrieve owned ticket details.
- `POST /api/tickets/:id/attachments`: Upload attachment file.
- `GET /api/attachments/:id`: Retrieve single attachment metadata.
- `GET /api/attachments/:id/download`: Download active attachment file.
- `DELETE /api/attachments/:id`: Soft-remove attachment with reason payload.

*(Full JSON schemas and status codes documented in `docs/lab-02/api-spec.md`)*

- **AC-07**: Given My Tickets screen, when searching for keyword "Wi-Fi", then list filters dynamically to show only matching tickets.
- **AC-08**: Given mobile viewport (< 768px), when viewing My Tickets, then list automatically renders in responsive card format without horizontal overflow.
- **AC-09**: Given invalid form input (summary < 5 chars or description < 10 chars), when Requester clicks Submit, then inline validation messages appear below the respective fields and API is not called.
- **AC-10**: Given My Tickets screen, when selecting Category, Priority, or Status filter dropdowns, then list updates dynamically to show only matching items.
- **AC-11**: Given My Tickets screen, when toggling Sort dropdown (Date Newest/Oldest vs Priority), then list ordering updates accordingly.

- **AC-14**: Given active Requester Selection dropdown, when switching context from Requester A to Requester B, then the application reloads ticket list for Requester B context.

## 11. Assumptions and Decisions

1. **Development Requester Header**: Requester identity is sent via HTTP Header `x-requester-id` to simulate logged-in user context in REST requests.
2. **Database Composite Index Decision**: A composite index `(requesterId, createdAt DESC)` is defined on the `Ticket` table. This decision optimizes the primary query in Sprint 2 (`GET /api/tickets` filtered by `requesterId` and sorted by `createdAt`), eliminating database filesort operations and ensuring fast pagination response times as ticket volume grows.
3. **Attachment Transaction & Compensation Strategy**: Because ticket creation (`POST /api/tickets`) and file attachment uploads (`POST /api/tickets/:id/attachments`) are separate API calls, transactional integrity is managed via a two-stage compensation strategy:
   - Stage 1: The ticket entity is created in PostgreSQL with status `NEW` and assigned an official Ticket Number.
   - Stage 2: Attachments are uploaded sequentially. If an attachment upload fails (e.g. storage error), the ticket remains safely created, and the user is presented with a non-blocking warning notification with an option to attach missing files from the Ticket Detail view. Orphaned temporary files from aborted uploads are automatically cleaned up by disk garbage collection.
4. **Soft Removal Storage Strategy**: Soft-removed files remain physically on disk in scratch/uploads storage to preserve audit metadata display, but the download endpoint returns HTTP 410 Gone for soft-removed files.
